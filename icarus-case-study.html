iCarus.
A player whose look is a setting.

What if a media player could wear any interface, including the hand-made skins of the early 2000s, without changing how it plays? iCarus separates what the player does from how it looks, and it downloads what you listen to.

ROLE
Concept, UX and interaction design, SwiftUI development

2026

01 / SUMMARY

One player, any interface.

iCarus is a macOS media player with two modes. Get is a front end for downloading music and video. Play is a player with a queue, a 10-band equalizer, a live visualizer and video. Every screen in Play is drawn by a skin, and the app can import Windows Media Player skins (.wmz), including the ones that run their own JavaScript.

This is a personal design and engineering project. The question was how far a player’s identity can be separated from its function, and what the experience of importing someone else’s interface should feel like when it only partly works.

02 / THE PROBLEM

Players look alike, and getting music in takes several tools.

  • Sameness. Most players share one look, so there is no personality and little room to make it yours.
  • A split workflow. One tool downloads, another tags, another plays.
  • A lost design culture. Windows Media Player skins were small works of interface design, and many are now hard to run at all.

The design question sat between two risks. If skins change the look but also the behavior, a bad skin breaks playback. If skins are locked down, there is nothing to express.

03 / GOALS

What it should do, and what it should not claim.

Goals

  • Keep playback identical whatever the skin looks like.
  • Run real Windows Media Player skins, not a lookalike format.
  • Tell the person plainly what an import could not do.
  • Make downloading feel like part of listening, with files landing in Play.
  • Stay safe when a skin carries code.

Non-goals

  • Being a full Windows Media Player replacement.
  • Supporting every skin. Some rely on features that are not built yet.
  • Formal usability validation at this stage.
04 / PROCESS

Build a piece, run it, report what broke.

I set the direction and made the design decisions, and built the code with Claude as a development partner. Each piece was written, then compiled and run on my Mac, and what failed or felt wrong drove the next change.

  1. Engine and built-in skins
  2. Image-based skins
  3. Windows Media Player importer
  4. Scene tree for each skin
  5. Script sandbox
  6. Live bindings to the player
  7. Motion and timers
  8. Playlist, tooltips, fonts
  9. Get and its Advanced tab

Real skins were the test suite. Two of them, Cerulean and Cyberchannel, each broke a different assumption about shape, color and button layout.

05 / KEY DECISIONS

Where the structure protects the experience.

5.1

One engine, many skins

Functionality lives in the player engine and presentation lives in skins. A skin is a folder with a description file and images, so a new look can add or remove controls but cannot change how audio is played. The built-in skins (Classic, a compact Midnight, Retro Radio, Sunset) show the range of colors, type and spacing the same engine can carry.

5.2

Import an existing format

Instead of inventing a skin format and starting with nothing, the importer reads Windows Media Player skins. It cuts out the transparent window shape, maps the skin’s buttons and sliders to the player’s controls, and keeps the layout as a tree. That gave the project a library of real, hand-made designs to meet and a reason to be strict about edge cases.

5.3

Say what did not work

Imports often succeed only in part. After installing, iCarus lists what it could not map, and a Skin Inspector shows the skin’s element tree, lets you hide parts and shows the script log. The person is never left to guess why a button does nothing.

5.4

Scripts, with limits and consent

Many skins carry JavaScript, and supporting them breaks the “skins are data” rule. I allowed it with a sandbox: a script sees only a small copy of the player’s object model, cannot reach files, the network or other programs, and runs only for a skin the person imported and allowed. Links open only for web addresses and only on a click.

5.5

Get feeds Play

Get has a Basic tab for the common case: paste a link, pick a format, download. An Advanced tab exposes quality, file naming, playlist and time ranges, subtitles and more, and shows the exact command so nothing is hidden. Finished downloads appear in Play, and the cover art that comes with each song fills the player when there is no video. Options that could run other programs are blocked.

5.6

Small moments of feedback

Resetting the equalizer glides every band back to neutral instead of snapping, so the person sees what changed. Buttons show tooltips, long titles scroll, and shaped, borderless skin windows can still be dragged. These are minor, but they are what makes an imported skin feel like it belongs to the player.

06 / PROBLEMS FOUND

What broke, and what I changed.

The import button did nothing
Two file pickers were nested inside each other, so the click was swallowed. Replacing them with a single native open panel fixed it.
Skins with similar colors mapped the wrong buttons
The importer matched button colors with a tolerance, which merged colors that were close but different. It now matches exactly first and only then allows a small tolerance.
Shaped windows could not be dragged
Clicks on artwork passed through to the window below and the drag never started. It took two attempts, ending with a drag surface of my own, and moving a borderless skin window now works.
Unsupported parts disappeared silently
Early imports dropped what they could not handle. That led to the post-import report and the inspector.
Unsafe download options
Free-text options for the downloader could have run other programs. Those flags are blocked and the rest are checked before a download starts.
07 / OUTCOME

Working today, and what is still missing.

Working today

  • Playback, the 10-band equalizer, the live visualizer and downloading.
  • Import of Windows Media Player skins, including their scripts. Cerulean and Cyberchannel run end to end in the app.
  • Playlist pane, tooltips, scrolling text, shaped-window dragging and the equalizer glide.

Still missing

  • Sounds, fullscreen video and effect presets.
  • A time limit for skin scripts, so a faulty skin cannot freeze the app.
  • Coverage of the wider skin library, which has not been run in the app yet.
08 / WHAT I LEARNED

Lessons for the next version.

  • Separating function from appearance is a design decision as much as a technical one. It is what lets people experiment without breaking anything.
  • When you accept work you did not author, failure is part of the interface. A clear report of what did not work earns more trust than a silent best effort.
  • Real, messy examples find problems that invented test cases never do.
  • Allowing code in a skin trades safety for fidelity, so the limits and the consent step have to be designed, not just implemented.
  • Small feedback, like the equalizer glide, makes a tool feel considered.
09 / NEXT STEPS

What I would do next.

  • Add a time limit for skin scripts, then build sounds, fullscreen video and effect presets.
  • Run a small usability study on first use: can people go from a pasted link to a playing song, import a skin, and understand why something did not work?
  • Test the importer on more skins and track what fails most often.
  • Do an accessibility pass: keyboard control for every skin, VoiceOver labels for imported controls, a reduced-motion setting for the visualizer and equalizer glide, and a contrast check for skins I do not control.
